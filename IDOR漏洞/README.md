## 核心概念速记

### IDOR 是什么

```
IDOR = Insecure Direct Object Reference（不安全直接对象引用）
```

- 应用直接把用户提供的 **对象标识符（ID、UUID、编号）** 拿去查数据
- **没有校验**这个对象是否属于当前用户

### 越权的分类

| 类型 | 英文 | 含义 | 例子 |
|------|------|------|------|
| 水平越权 | Horizontal | 同级用户之间互访 | 学生A访问学生B的数据 |
| 垂直越权 | Vertical | 低权限访问高权限功能 | 学生访问老师的接口 |

> IDOR 是越权的一种子集，重点是"改对象引用参数"导致的越权（大多数是水平越权）。

### 判断是不是 IDOR

遇到一个接口，问自己：

1. 请求里有没有 **ID / UUID / 编号 / 文件名** 这类标识符？
2. 如果把它改成**别人的值**，返回的内容会变吗？
3. 服务端有没有校验"这个对象是我的"？

**三个都 yes → 大概率是 IDOR。**

## 角色标志常见位置

系统判断"你是不是管理员"，总得有个地方记录身份：

| 位置 | 例子 |
|---|---|
| Cookie | `Admin=false` |
| 请求参数 | `?role=user` |
| 请求头 | `X-Role: user` |

> 如果服务端从**请求里**读取角色标志，攻击者就能自己改成 admin。

## 实战方法论（发现管理接口 + 垂直越权）

参见 [[IDOR漏洞/实战方法论_发现管理接口与垂直越权测试]] — 核心是**用自己账号测越权**，不靠拿别人的 Cookie。

| 方式 | 说明 |
|---|---|
| 重放管理接口 | 低权限直接调高权限接口，接口没鉴权 |
| 改角色参数 | Cookie/参数里的 Admin=false → true |
| Mass Assignment | 修改资料时提交 roleid 提权 |
| JWT/Token 伪造 | 硬编码凭据、签名算法绕过 |
| 方法/路径绕过 | 换方法、加 X-Original-URL 头 |

## 通用方法论

1. **梳理角色**：系统有哪些角色？普通用户 / 管理员？
2. **找角色判定点**：服务端怎么判断"你是什么角色"？（Cookie / 参数 / 头 / 数据库）
3. **测垂直越权**：低权限账号能不能调高权限接口？
4. **测水平越权（IDOR）**：改对象 ID 能不能看别人的数据？
5. **测批量赋值**：修改资料接口会不会把请求里的字段直接写库？

## 防御红线

- **角色权限必须在服务端校验**，不能信任客户端传的角色标志
- **对象级授权**：访问前校验对象归属
- **禁用/白名单化批量赋值**（Mass Assignment）
- **隐藏管理路径**：不能只靠"不暴露链接"防，必须做鉴权

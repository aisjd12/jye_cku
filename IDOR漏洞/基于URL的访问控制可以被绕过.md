# 基于URL的访问控制可以被绕过

来源：PortSwigger Web Security Academy  
靶场：URL-based access control can be bypassed（基于URL的访问控制可以被绕过）

## 知识点

### 漏洞本质：前端/后端双轨制

这个系统的访问控制分两层：

| 层 | 看什么 | 做了什么 |
|---|---|---|
| **前端路由** | 浏览器地址栏/真实请求路径 | 拦截 `/admin`，渲染权限不足 |
| **后端路由** | 特定请求头 | 按 `X-Original-URL` 的实际值处理 |

关键：
> 前端只拦了**地址栏路径**，但后端可以读**请求头里的路径**。

### 核心绕过方式

用**无害路径**通过前端，再用请求头把真实目标路径告诉后端：

```
前端：GET /foo → 没问题，放行
后端：X-Original-URL: /admin → 按 /admin 处理
```

### 常见相关头

| 请求头 | 说明 |
|---|---|
| `X-Original-URL` | 部分框架/中间件用于记录原始请求路径 |
| `X-Rewrite-URL` | 类似用途的路径重写头 |

> 只要后端根据这些头做路由，而前端只看真实路径，就可能出现访问控制旁路。

## 通关过程

### 1. 确认前端拦截

直接访问：

```
GET /admin
```

被前端拦截，返回“未找到”/权限不足页面。

### 2. 绕过前端，进入管理面板

构造请求：

```
GET /foo
X-Original-URL: /admin
```

- 路径 `/foo` → 前端放行
- 头 `/admin` → 后端按管理面板处理

### 3. 执行敏感操作

进入 `/admin` 后，用同样方式构造删除请求：

```
GET /foo
X-Original-URL: /admin/delete?username=carlos
```

**注意**：查询参数 `?username=carlos` 是写在 `X-Original-URL` 的值里，不是写在真实路径里。

## 易错点 / 踩坑

| 坑 | 原因 | 解决 |
|----|------|------|
| 真实路径仍写 `/admin` | 前端继续拦截 | 改成 `/`、`/foo` 等无害路径 |
| 把参数写在真实路径 | 后端不看真实路径参数 | 把 `?username=carlos` 放进 `X-Original-URL` |
| 只用 POST 测 | 这关是 GET 路径绕过 | 保持 GET，改路径和头 |
| 只改头不改路径 | 有些实现路径也要避开敏感词 | 路径和头配合，双管齐下 |

## 防御建议

1. **访问控制在服务端统一执行**，不要前端拦完就完事。
2. 后端路由不要信任客户端提供的路径类请求头。
3. 对 `X-Original-URL`、`X-Rewrite-URL` 等头做白名单或忽略处理。
4. 前后端统一权限校验逻辑，避免双轨判断不一致。

# 用户 ID 由请求参数控制，数据泄露则重定向

来源：PortSwigger Web Security Academy  
靶场：User ID controlled by request parameter, with data leak in redirect

## 知识点

### 漏洞本质

用户资料/个人主页接口通过**请求参数里的用户 ID** 查数据，但服务端**没有校验当前会话是否属于该 ID**。

攻击者把参数改成别人的 ID，就能访问别人的资料；若目标接口把敏感信息写进 `Location` 重定向，敏感信息会直接出现在响应头里。

### 为什么更危险

很多系统只校验“你有没有登录”，不校验“你能不能看这个用户的数据”。这属于**水平越权 / IDOR**。

## 通关过程

### 1. 登录普通账号

登录 `wiener:peter`。

### 2. 访问自己的个人主页

访问 `/my-account?id=wiener`，记录你的 ID 和页面内容。

### 3. 改成其他用户 ID

把 URL 里的 `id` 改成目标用户 ID（如 `carlos`）：

```
GET /my-account?id=carlos
```

看响应头里的 `Location` 是否泄露敏感信息。

### 4. 利用重定向泄露

若目标页面会先把用户 ID 或邮箱拼进 `Location`，那就从响应头里直接拿到信息。

## 易错点 / 踩坑

| 坑 | 原因 | 解决 |
|----|------|------|
| 只改一次 | 不知道目标 ID 就先枚举 | 用 `wiener` 和常见用户名试 |
| 只看页面不看响应头 | 数据泄露点在重定向 | 看 `Location` / `Set-Cookie` |
| 用 POST 再测一次 | 这关是 GET 页面 | 保持请求方式一致 |

## 防御建议

1. 访问对象前校验**当前会话是否拥有该对象**。
2. 不要在重定向中回显敏感字段。
3. 对象标识符不要使用可枚举/可猜测的序列。

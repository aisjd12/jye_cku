# 用户角色可以在用户配置文件中修改

来源：PortSwigger Web Security Academy  
靶场：User role can be modified in user profile（用户角色可以在用户配置文件中修改）

## 知识点

### 漏洞本质：Mass Assignment（批量赋值）

修改资料接口把请求体里的**所有字段**直接写入数据库，且**没有过滤敏感字段**。

于是客户端可以顺手提交 `roleid`，把角色改成管理员。

```
正常请求：{"email":"..."}
恶意请求：{"email":"...", "roleid": 2}
→ 服务端把 roleid 也写进用户记录 → 提权
```

### 为什么服务端会这样

- 框架把 JSON body 直接反序列化成用户对象
- 然后 `save()` 整个对象
- 没有做**字段白名单** → 攻击者传入的 roleid 也保存了

## 通关过程

### 1. 拿到成功基准请求

浏览器正常修改邮箱，Burp History 里找到成功的请求：

```
POST /my-account/change-email HTTP/2
Content-Type: text/plain;charset=UTF-8

{"email":"965@qq.com"}
```

响应返回整个用户对象，泄露了当前角色：

```json
{
  "username": "wiener",
  "email": "965@qq.com",
  "apikey": "...",
  "roleid": 1
}
```

### 2. 让目标告诉你目标 roleid

访问 `/admin`，看报错提示里写了需要什么角色 ID。

### 3. 修改 roleid 提交

把 body 改成：

```json
{"email":"965@qq.com", "roleid": <目标值>}
```

> ⚠️ JSON 字段之间**必须有逗号**，否则解析失败！

### 4. 验证提权

- 刷新个人页面，角色变成 Admin
- 访问 `/admin` → 删除 carlos → 完成

## 易错点 / 踩坑

| 坑 | 原因 | 解决 |
|----|------|------|
| **JSON 少逗号** | `{"email":"..." "roleid":2}` 语法错误 | 字段之间加 `,` |
| 猜 roleid 的值 | 不知道管理员是多少 | 访问 /admin 看提示，让目标告诉你 |
| 在 /admin 请求里找 roleid | 混淆了两个请求 | roleid 在**修改资料请求**里改，改完再去 /admin |
| 手工从头写请求 | 格式容易错 | 从 Burp History 复制成功请求再改 |

## 防御建议

1. **字段白名单**：更新接口只接受允许修改的字段（如 email）。
2. **角色字段服务端控制**：roleid 不允许客户端提交。
3. 使用 DTO（数据传输对象）替代直接绑定实体类。

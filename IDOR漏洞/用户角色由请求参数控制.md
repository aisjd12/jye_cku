# 用户角色由请求参数控制

来源：PortSwigger Web Security Academy  
靶场：User role controlled by request parameter（用户角色由请求参数控制）

## 知识点

### 漏洞本质

服务端从**请求（Cookie/参数/头）**里读取角色标志来判断权限，而不是从数据库校验。

攻击者可以**自己修改角色标志** → 提权成管理员。

### 角色传递的三种位置

| 位置 | 例子 |
|---|---|
| Cookie | `Admin=false` |
| 请求参数 | `?role=user` |
| 请求头 | `X-Role: user` |

> 关键：**角色不能由客户端控制**。一旦客户端能改角色标志，垂直越权就成立。

## 通关过程

### 1. 登录普通账号

登录 `wiener:peter`，访问 `/my-account`。

### 2. 找角色标志

抓包看登录后响应，重点看 **Set-Cookie**：

```
Set-Cookie: Admin=false; ...
```

发现一个布尔字段 `Admin=false`。

### 3. 修改角色标志

把 Cookie 里的 `Admin=false` 改成：

```
Admin=true
```

### 4. 访问管理后台

带 `Admin=true` 的 Cookie 访问 `/admin` → 进入管理面板 → 删除 carlos。

## 易错点 / 踩坑

| 坑 | 原因 | 解决 |
|----|------|------|
| 以为是改请求 ID | 混淆了 IDOR 和角色提权 | 这关改的是**角色标志**，不是对象 ID |
| 只改 Body 不改 Cookie | 角色在 Cookie 里 | 找到角色实际存放的位置 |
| 用扫描器直接跑 | 不理解角色校验机制 | 抓包分析登录响应里的角色字段 |

## 防御建议

1. **角色权限在服务端判定**，从会话/数据库取，不信任客户端。
2. Cookie 里不要放可篡改的角色标志；如有，需加密/签名。
3. 敏感操作二次校验角色。

知识点：
1. 漏洞核心：服务端只检查 Token 是否存在，不校验有效性

- 正常请求带 csrf Token → 服务端校验 Token 值。
- 把 Token 值改成随机字符串 → 服务端拒绝。
- 但**删除整个 csrf 参数** → 服务端跳过校验，请求仍然成功。

```
有 Token + 值正确  → 通过 ✓
有 Token + 值错误  → 拒绝 ✗
无 Token           → 跳过校验 ✗ → 仍然执行
```

2. 漏洞成因

- 服务端逻辑可能是：
  - 如果请求中包含 csrf 参数 → 校验其值。
  - 如果请求中不包含 csrf 参数 → 跳过校验。
- 这是一种有缺陷的防御实现：只检查"有没有"，不检查"对不对"。

3. 测试方法

| 测试 | 操作 | 预期结果 |
|------|------|---------|
| 基准 | 原始请求不动 | 成功 |
| 删值 | csrf 值改成随机 | 拒绝 |
| 删参数 | 删除整个 csrf 参数 | 成功（漏洞） |
| 空值 | csrf=（空） | 视实现而定 |

4. 防御方案

- Token 不存在时必须拒绝请求，而不是跳过校验。
- 使用成熟框架的 CSRF 中间件，不要自己实现。

通关过程：
1：登录账号，抓到 `POST /my-account/change-email` 请求，Body 中有 `csrf` Token
2：在 Repeater 中把 csrf 值改成随机字符串 → 发送 → 服务端拒绝
3：删除整个 csrf 参数 → 发送 → 邮箱修改成功，说明 Token 不存在时跳过校验
4：在 Exploit Server 构造 PoC，表单中**不包含 csrf 参数**：
5：只有 `email` 隐藏字段 + 自动提交脚本
6：Store → Deliver exploit to victim → victim 邮箱被修改 → 靶场解决

易错点：
- 以为 Token 值改了就是绕过 → 删值会被拒绝，必须删整个参数。
- PoC 中仍然带了 csrf 参数 → 服务端会校验其值并拒绝。
- 以为 Burp 自动生成的 PoC 一定可用 → 需要手动删除 csrf 字段。

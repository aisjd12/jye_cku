# 带有黑名单输入滤波器的SSRF

> 官方名：SSRF with blacklist-based input filter。核心：目标对 SSRF 的可控 URL 做了字符串黑名单过滤，例如禁止 `localhost`、`127.0.0.1`、`/admin`，但过滤不完整，导致可以用等价写法或二次编码绕过。

## 知识点：黑名单过滤为什么容易绕过

黑名单的思路是：

```text
用户提交 URL
    ↓
检查是否包含 localhost / 127.0.0.1 / admin 等危险字符串
    ↓
不包含才允许服务器请求
```

问题是同一个地址、同一个路径有很多等价表示方式：

```text
http://localhost/admin
http://127.0.0.1/admin
http://127.1/admin
http://0177.0.0.1/admin
http://2130706433/admin
http://loc%61lhost/%61dmin
http://loc%2561lhost/%2561dmin
```

只要黑名单没有覆盖所有等价形式，就可能被绕过。

## 知识点：二次 URL 编码

### 一次编码

字母 `a` 的十六进制 ASCII 是 `61`，因此：

```text
a → %61
```

### 二次编码

如果对已经编码后的字符串 `%61` 再编码一次，重点是把 `%` 本身也编码：

```text
% → %25
%61 → %2561
```

所以：

```text
a → %61 → %2561
```

`%2561` 不是“字母 `a` 的普通显示形式”，它是需要**解码两次**才能得到 `a`：

```text
%2561
  第一次解码：把 %25 解码为 %
  结果：%61
  第二次解码：把 %61 解码为 a
  结果：a
```

## 为什么二次编码有时能绕过黑名单

典型流程：

```text
客户端提交：http://loc%2561lhost/%2561dmin
        ↓
过滤层解码一次：http://loc%61lhost/%61dmin
        ↓
黑名单检查：没有直接匹配 localhost、admin
        ↓
后续处理或后端再解码一次
        ↓
实际请求：http://localhost/admin
```

本质是：**过滤层和实际解析层对 URL 的解码次数不一致**。

## 通关过程

1. 找到可控的服务器端请求参数，例如库存检查里的 `stockApi`
2. 先尝试正常访问本地管理接口：
   ```text
   http://localhost/admin
   ```
3. 观察响应，确认应用拒绝了 `localhost` / `127.0.0.1` / `admin` 等常见黑名单字符串
4. 改用大小写、短格式 IP、十进制 IP、二次编码等等价形式测试
5. 成功绕过后，从返回的管理页面中确认删除用户的接口路径
6. 构造删除用户的 SSRF 请求，删除指定用户后完成靶场

## 常见绕过写法

| 原始值 | 绕过思路 | 示例 |
|--------|----------|------|
| `localhost` | 大小写混合 | `LoCaLhOsT` |
| `127.0.0.1` | 省略零的回环地址 | `127.1` |
| `127.0.0.1` | 八进制 IP | `0177.0.0.1` |
| `127.0.0.1` | 十进制整数 IP | `2130706433` |
| `localhost` | 字母一次编码 | `loc%61lhost` |
| `localhost` | 字母二次编码 | `loc%2561lhost` |
| `/admin` | 字母编码或大小写混合 | `/%61dmin`、`/ADMIN` |
| 固定地址 | 外部域名解析到本机 | 可控域名 / Collaborator 相关域名 |

> 实际是否可用取决于应用在哪一层做检查、检查前是否解码、请求库是否再次解码。

## 易错点（我的踩坑）

### 1. 以为 `%2561` 还是 `a`

一开始不理解二次编码：

```text
a → %61
%61 → %2561
```

关键是第二次编码时，被编码的是 `%`，所以会变成 `%25`。

### 2. 很多工具默认不编码字母

URL 编码中：

```text
A-Z
a-z
0-9
- _ . ~
```

属于 unreserved characters，很多工具默认不编码，所以你输入 `a` 得到的还是 `a`，而不是 `%61`。

因此想得到 `%2561` 时，有两种方法：

1. 手动把 `%` 编码成 `%25`
2. 使用支持全量 URL 编码的工具，或者自己写脚本处理

### 3. 编码不是“显示成什么”，而是“解码次数”

同一个逻辑字符串：

```text
a
%61
%2561
```

在只看显示时它们不同，但经过不同次数 URL 解码后，可能都代表 `a`。

判断绕过时要问：

```text
过滤层解码几次？
请求层解码几次？
最终 URL 是什么？
```

### 4. 黑名单判断要区分“请求前”和“请求时”

有些代码是在原始字符串上匹配 `localhost`：

```text
http://loc%2561lhost
```

看起来不包含 `localhost`，于是放行。

但后续组件解码后得到：

```text
http://localhost
```

于是 SSRF 成功。

## 防御建议

- 不使用黑名单，改用**严格白名单**
- 只允许固定协议、固定域名、固定端口和固定路径模板
- 校验前先标准化 URL，并处理重复编码
- 解析 DNS 后校验真实 IP，禁止回环地址、内网段、链路本地地址和云元数据地址
- 禁止 HTTP 重定向自动跟随，或重定向后重新校验目标
- 出网请求服务部署在独立网络分区，与内部管理接口隔离
